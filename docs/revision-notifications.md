# 同日修订通知

首次晨报沿用完整标题列表、详情链接和原海报。首次投递之后，事实纠错或重要新增发送一条简短文字更新；排版、普通链接修复和措辞调整更新网页。修订不重发整份日报或海报。

新修订使用 `schema_version: "1.1"`，保留完整正文、条目、图片及原有来源/去重校验，并在 `report.json` 增加：

```json
"revision_notice": {
  "kind": "correction",
  "summary": "更正实验所用硬件与适用条件，原结论相应收窄。"
}
```

`kind` 为 `correction`（重要事实纠错）、`material_update`（重要新增）或 `maintenance`（非实质修订）。`summary` 是非空单行，最多 600 UTF-8 字节，不含 HTML。作者/编辑按来源证据判断类别，说明随报告 PR 审查，不能由文件哈希变化推断重要性。重要修订的说明应概括本日首次发布以来仍有效的重要变化，供连续未发送修订合并；普通修订不得撤回或改变事实结论后仍标为 maintenance。

请求身份为 `morning-YYYYMMDD-rN`，版本按现有规则递增。历史 1.0 快照及其已有发送意图继续按原契约读取，保持原字节；新的修订 delta 必须声明 1.1 通知策略。

交互桥先使用无回显 stdin pipe，或为 PTY 设置 `stty -echo -echonl -icanon`，避免原生 ticket 签名 URL 回显；操作细节沿用 [研究归档交互桥](research-archive.md)。使用 `node scripts/slack-stage-cli.mjs /absolute/ai-brief-bundle.json PINNED_CHANNEL --revision-managed-proxy`，按原交互桥转交原生工具请求和结果。工具上传完整原包，完成说明为 `!ai-report revise morning-YYYYMMDD-rN BUNDLE_SHA256`。已安装的私有提交策略认证原 sender/App、频道、文件、来源时间和原字节，持久记录后进入原报告 PR/合入流程；该入口不占用 r1 的 staged 日期槽或 new-daily 研究 permit。任何旧日期隔离、原请求冲突和未知写入仍按原记录对账。同日既有 Publisher 作业先完成原发布回执，再准入下一修订；这不等待企微队列发送完成，尚未发送的企微计划仍可接续。Publisher 自动交接每一个已核验版本，包括 maintenance。结果不明时读取原文件、原命令及该修订状态，保留一次上传意图。

更新格式为日期、重要更正/重要更新、简短说明和该日稳定链接。新通知绑定日期、版本、报告提交和原包哈希；稳定网址相同不会合并首次投递与修订身份。真实成功为 `sent / complete`、`1/1`、无图片。网页更新明确记为 `skipped / web_only`，不冒充发送成功。

## 首次推送与连续修订

- 首次尚未进入发送边界时，最新已核验版本承担完整首发。原任务、分片和日期声明保留，通过持久 supersession 关联新请求，原请求不记为 sent。
- 首次已有成功或未知分片时，保留原回执和未知状态，停止尚未开始的过时计划；重要修订单独发送文字。未知请求不因改版而重试。
- 新版本合并确认尚未发送的修订时，记录被覆盖请求及原记录哈希。maintenance 承接已有待发的重要说明，不能把它取消。发送中或结果未知的相同文字不换 ID 重发；已成功后新重要修订可独立通知。
- 发送与 supersession 争用同一 SQLite 写事务；撤销验证租约后，旧验证器的迟到结果不能恢复发送。确切失败按既有退避重试，未知保持冻结。次日独立任务继续运行。

## 部署与验收

Publisher、固定 Node verifier、relay 队列及本机 scheduled client 必须配套升级；新格式由真实来源校验器生成计划，外部请求不能选择目的地或注入 verified 标志。两张新操作表仍位于原 relay 数据库，正文和报告历史继续以 Git 为准。

隔离回归覆盖首次未发/部分成功/未知、连续修订、maintenance 承接重要更新、验证与替换竞争、重复准入、失败重试和未知跨日隔离。生产验收记录代码版本、CD、原数据库身份及原回执；不为测试给收件人发送虚构更正。
