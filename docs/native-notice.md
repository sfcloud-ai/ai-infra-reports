# 原生 Slack 工具接线

此桥接复用已授权的私有控制频道、Publisher 账本和原生 Slack 工具身份。`native-notice-cli.mjs` 只生成数据和核验真实工具结果，不创建凭据，也不调用 Slack。新增的[定时宿主实现](native-scheduled-host.md)串联这些步骤与原生工具，默认在 `begin` 前停止；它尚未接入实际定时任务。需要具备原生工具与代码执行能力的定时宿主按下列顺序执行；仓库 CI 通过不等于该宿主已接线。

1. 固定本次仓库及 Prompt 提交，完成报告包提交、自动合入和各页面/原图验证。随后从保存的同一 `report.json` 生成通知，标题及 URL 顺序完全一致，正文不加摘要。
2. 提前调用 `slack_get_file_upload_url`，按原生工具返回的签名 URL 原样 POST 最终海报字节。使用这次返回的 `file_id`；此时不调用 `slack_complete_file_upload`。已验证原生上传可保留约 15 分钟，宿主应在发送前约十分钟准备；保留更长时间尚未验证。
3. 通过 `command` 模式生成新的 `prepare` JSON，以 `ai-notice-command.json` 文件及程序生成的 `initial_comment` 完成上传到固定控制频道。Publisher 只记录预约，回复 `send_authorized:false`。重启后可通过新 `status` 命令读取原预约，不重新申请文件或替换身份。
4. 当前新执行生成新的 `begin` 命令。在收到回执前，T4 已原子写入唯一 `completion_intent`；同一日报之后的 `begin` 均不能取得新的发送许可。可提前取得此次许可，回执中的 `not_before` 固定为报告日期的北京时间 08:00。宿主必须等待到该时刻才能完成正式文件上传。
5. 使用 `command` 输出的 `receipt_search` 原样调用 `slack_search_public_and_private`。把实际调用名称、参数和原始结果一起交给 `receipt`/`complete` 模式。搜索必须限定固定频道和 Publisher 用户 ID、包含机器人且不带上下文；唯一结果的工作区域名、频道、线程、命令 ID、命令字节哈希都必须吻合。原生工具不提供原始 bot/app 字段，此适配器不伪造这些字段，也不改变旧 raw API 校验器。
6. 正式完成前一分钟内重新验证公开页面、原始海报和本次上传字节。`checked_at` 必须在这一轮检查开始前记录；超过 60 秒就重新检查，不能在检查结束后刷新时间掩盖陈旧结果。到 08:00 后，`complete` 模式才输出唯一一次 `slack_complete_file_upload` 的参数：固定正式 DM、原始文件 ID、各篇标题/URL 和一张海报；不附线程参数。
7. 真正调用完成上传后，回读实际顶层消息与原图，通过现有 `check` 请求让 T4 独立验证，匹配后再提交 `record`。Slack 上传结果、T4 检查和企微文字/图片回执分别核实。任何未知完成结果只核对原消息，不能再次调用完成、申请替代文件或重发。

每次宿主执行都必须生成新的命令 ID。只有本次新 `begin` 的回执可用于唯一一次完成调用；进程重启、任务重试或丢失调用结果之后，旧许可只能用于核对，不能恢复发送。T4 持久意图使新执行无法再申请另一份许可。

`asset` 命令可核对控制频道中已完成上传的海报原始字节：预期哈希和大小来自保存的报告包，严格核对上传身份、工作区、文件所有者、分享范围及原始下载 URL。它不会预约或授权正式发送。它不能读取仍未完成的预上传文件，也不能替代正式 DM 的独立检查。

今晚测试只允许控制频道文件和 T4 处理；实际通知序列化仍走真实 relay/WeCom 代码，但在最终 HTTP 请求处拦截。禁止为测试完成正式 DM 上传或触发企微。当前仍需要宿主实际接线、真实新版横版海报验证和完整演练；零入选通知也尚未由此接口实现。
