长上下文的 KV 离开 GPU 后，稀疏注意力仍需要先找到该读哪些 token。如果把“用于选 token 的索引页表”和“用于读取注意力 KV 的页表”混作一套，主机缓存、GPU 工作区和共享前缀的生命周期就会互相干扰。超配首先要保证读到正确状态，再讨论能放入多少请求。

### 从索引选择到实际 KV 读取

**DSA 索引页表选出位置 → HiCacheBuffer 解释 device/host 索引 → 读取 GPU 常驻 KV 或主机页 → 填充请求自己的 GPU 工作区 → 注意力计算**。新增可选的独立 DSA indexer page table：显式提供时使用，未提供仍沿用 attention 的 real page table；新增缓冲区支持后绑定 host buffer，并为每个请求维护 LRU。

这与“把一块 GPU 内存直接扩成更大内存”不同：主机页可以承载共享前缀，GPU 工作区仍属于具体请求，地址转换和回收必须分别管理。BF16/FP8 字节保真、容量边界、请求复用及 graph replay 的回归，验证的是这层数据管理行为，不能替代端到端调度和负载测试。

### 超配的预算仍要逐项算

多个模型并驻时，**独立权重 + KV/循环状态 + 激活与工作区 + 传输缓冲及安全余量**仍须纳入预算。这不是 CUDA UVM，也不提供跨模型任意共享权重或 KV 的依据。把 KV 放到主机，只是把部分容量压力转成传输与调度压力；多租户隔离、命中率和尾延迟仍决定能否稳定服务。

本次没有可归属于该补丁的完整吞吐、TTFT 或超配倍率测量。面向 H100/H200，应先确认生产路径实际启用，再固定模型、前缀共享比例、上下文长度和并发，测主机↔GPU 流量、驱逐/回填、OOM 与 p99 延迟。Pro5500（型号待核实）不能从这里推定兼容或收益。
