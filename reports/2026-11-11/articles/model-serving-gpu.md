# 模型副本快速恢复与 Agent 缓存调度：两条降低 GPU 等待成本的路径

今天的两项进展解决的是不同层次的问题：NVIDIA Snapshot 减少一个新副本开始服务前的初始化等待；Evolving Infra 尝试让已经运行的推理集群随 Agent 工作负载调整资源和缓存。两者都与利用率有关，但不是同一个系统，也都不能证明“不同模型共享一份权重和 KV”。

## 1. NVIDIA Snapshot：让已经预热好的 GPU 副本更快回来

**进展日期：2026 年 11 月 10 日 15:00 UTC。** [NVIDIA 官方技术文章](https://developer.nvidia.com/blog/start-and-restore-gpu-workloads-in-seconds-with-nvidia-snapshot/)介绍独立开源的 Kubernetes GPU 检查点与恢复构件，并给出多引擎、单节点多 GPU 的测试矩阵。

### 为什么分配到 GPU 后还要等

一个模型服务副本获得 GPU，并不意味着马上能回答请求。它还要加载权重、初始化 CUDA 和运行库、编译或调优算子、捕获执行图。大型模型的这些步骤可能需要数分钟。突发流量来了再启动副本，用户可能先排队；始终保留热副本，则要为闲置容量付费。

Snapshot 的思路是：把已经完成初始化的进程状态保存下来，下次恢复这份状态，跳过重复初始化。检查点概念并非首次出现，Dynamo 已有相关集成；本次值得关注的是独立构件、生命周期接口和更具体的引擎测试结果。

### 数据和控制怎样流动

1. 源副本加载模型并至少完成一次真实生成，使惰性初始化、调优和执行图准备尽量发生在保存之前。
2. 工作负载停止在途生成，进入安全点。官方基准在检查点前释放 KV 缓存，即保存推理历史计算结果的那部分内存，以避免把不需要的缓存带进快照。
3. 控制器和节点代理通过 CRIU 与 CUDA 检查点能力，保存 CPU 进程及 GPU 初始化状态到共享存储。
4. 新副本引用快照，在兼容节点上恢复，等待恢复完成，再恢复引擎、检查健康状态和服务监听，最后接收流量。

在 Kubernetes 中，`PodSnapshot` 可以针对已有运行副本；`SnapshotJob` 可以从模板启动副本，等它准备好再保存；恢复副本通过 `nvidia.com/restore-from` 选择快照。具体何时缩容、恢复几个副本，仍要由上层服务平台编排。

这不是活跃聊天会话的通用无损迁移。这里测试的是**初始化状态恢复**，并非保存所有正在处理的请求。它也没有让独立模型共用权重，更没有把不同模型的 KV 变成一份通用缓存。

### 测到了什么，没测到什么

作者使用单节点 B200、驱动 615.71.09 和 VAST NFS，共测试 22 组配置，覆盖 vLLM 0.31.0、SGLang 0.5.21、TensorRT-LLM 1.3.0。恢复时间为 **3.59–42.69 秒**，相对相应冷启动的时间比为 **8.10–35.87 倍**。

两组例子说明尺度差异：

- vLLM、Qwen3-14B、单 GPU：冷启动 122.76 秒，恢复 5.72 秒；生成检查点需 19.98 秒，快照 37.71 GB。
- SGLang、DeepSeek-V4-Pro-NVFP4、TEP8：冷启动 621.55 秒，恢复 42.69 秒；生成检查点需 253.72 秒，快照约 1,039.09 GB。

这不是从零申请机器到接收用户流量的全部时间。基准不含基础设施准备、拉取镜像及容器运行时设置，也没有给出在线吞吐、请求 p99 或模型输出质量的对照。不能把“恢复更快”写成“推理速度提高几十倍”，也不能把 B200 的结果外推到 H100、H200 或 RTX PRO 5500。

### 交付条件比 API 数量更重要

[项目 README](https://github.com/ai-dynamo/snapshot)明确提示：API 仍可能变化，**尚不建议用于生产关键负载**。当前支持单节点多 GPU，不等于支持跨节点模型的完整恢复；vGPU 不受支持。

现有文档列出的前提包括 Linux 内核至少 5.13、NVIDIA GPU Operator 至少 26.3、禁用 MIG、驱动至少 580、共享 RWX 或 S3 存储，以及允许特权节点代理。恢复需要匹配的 GPU 硬件和驱动版本；工作负载配置也必须一致。[工作负载合同](https://github.com/ai-dynamo/snapshot/blob/main/docs/reference/workload-contract.md)要求先停止在途生成，等待实际恢复完成，不能仅凭一个就绪标记提前接流量。项目文档采用可变 main 链接；本文未确认不可变实现提交，不能据此视为固定版本部署验收。

对算力服务平台，更合理的试点是在非关键、同构 GPU 池中测试闲置模型缩到零副本、预留机器上的补副本和故障恢复。验收应包括端到端可服务时间、并发恢复时共享存储带宽、快照容量、机型或驱动升级后的重制成本，以及特权代理的隔离要求。只有这些成本小于保留热副本的成本，才可能形成实际收益。

## 2. Evolving Infra：Agent 会改写上下文，集群也要跟着变

**论文日期：2026 年 11 月 9 日 12:26:02 UTC，属于本期扩展至 72 小时的候选。** [Evolving Infra: Agent-Adaptive LLM Serving at Scale，v1](https://arxiv.org/html/2611.12304v1)提出把推理阶段调度与 Agent 上下文生命周期一起管理。

### 固定配比和普通缓存为何会失灵

推理有两个主要阶段：预填充（prefill）先读懂输入上下文，解码（decode）再逐步生成输出。读大量材料的任务和长篇推理任务，对两类 GPU 容量的需求不同。固定划分容易一边排队、一边空闲；重新启动引擎来换角色，又可能带来长时间停顿和缓存损失。

Agent 还会启动子任务、等待工具、压缩旧历史和结束分支。传统“最近最少使用”缓存策略只看访问时间，可能淘汰一个正在等工具、稍后还要继续的分支，却保留已经被压缩替换的历史。

### 四个机制需要一起看

**第一，让引擎不用重启就能换阶段。** 作者修改 SGLang，用一套调度循环支持预填充和解码。规划器重新分配角色时，路由器转移排队工作，让在途请求完成，再切换角色。基于 Mooncake RDMA 的双向 KV 传输继续可用。

**第二，把主机内存做成跨角色可读的 KV 池。** GPU 中的一级缓存写入本节点主机二级缓存；节点之间直接读取主机 KV。预填充请求还在队列里时就预取所需缓存，尽量用排队时间隐藏传输。解码的输入走 GPU 间传输，不让每一步生成都等待从主机拉取。

**第三，缓存淘汰看“哪个活跃分支还需要它”。** 目录记录分支对 KV 块的引用数及版本。分叉、压缩、结束和迁移更新这些记录，优先淘汰没有活跃分支引用的块。版本信息用于处理上下文改写和迁移交叠，不能只做一个简单计数器就认为正确性已解决。

**第四，按真正需要重算的工作量调整配比。** 规划器考虑前缀缓存命中，在线学习迭代耗时，使用 600 秒窗口、10 个时间片评估需求，避免把全部输入长度都算作新计算，也避免追逐很短的突发负载。

这些能力不是从零开始：Dynamo 已有缓存感知路由和规划器，SGLang 已有 HiCache，Mooncake 已有 RDMA 传输。论文的增量是角色切换、共享缓存与 Agent 生命周期的联合设计。其节点内去重针对同一模型的重复 KV，并不是让不同模型共用权重或 KV。

### 必须同时读最大收益和最佳静态基线

主要实验使用 9 个节点、每节点 4 张 GB300，共 36 GPU，每个引擎采用四路张量并行。模型为 GLM-5.2 和 Kimi K2.6，使用 NVFP4 权重、FP8 KV 和多 token 预测；主机 KV 可容纳的 token 数是 GPU KV 的四倍。

负载包括 Putnam 数学任务、OSWorld 2.0 计算机操作和真实 Claude Code 轨迹回放。每轮预热 30 分钟且不计入测量，之后以固定并发运行一小时；另有三小时负载组成变化实验。比较对象包括 Dynamo v1.5.1，以及调过路由策略、使用相同主机缓存容量的 SGLang 最佳静态阶段配比。

相对 Dynamo，作者报告吞吐提高 1.10–2.73 倍、平均端到端时延改善 1.15–4.12 倍、P95 首 token 时延最高改善 13.92 倍。但是，低并发下相对最佳静态配比的吞吐比仅为 **0.98–1.38 倍**，并非所有场景都胜出。

对现有 H200 资源池更相关的是附录实验：64 张 H200、16 个四路并行引擎，DeepSeek-V4-Flash，384 个 Claude Code 会话。测试过的静态方案中，8 个预填充引擎加 8 个解码引擎优于 9 加 7；Evolving Infra 在这个更强基线上进一步提高吞吐 **9%**。不能用主实验最大倍率代替这组硬件条件下的结果，也不能再外推到 H100。

还有两个容易遗漏的边界：

- 真实实验扩展到最多 256 GPU；3,072 GPU 是模拟，不是实机部署证明。
- 在 Putnam 的部分并发设置下，吞吐和端到端时延改善，但 P95 首 token 时延比 Dynamo 更差。更高利用率不自动意味着更好的交互等待体验。

### 适合研究试点，不宜当作现成配置开关

本文未确认作者提供完整公开实现和可直接运行的复现包。方案涉及引擎、路由器、Agent 分支信号、RDMA 内存管理和迁移一致性，接入与升级维护成本明显高于改一个缓存参数。

Claude Code 轨迹回放固定了输出长度和工具时长，不是完整 Agent 任务正确率验证。量化和 KV 精度是实验配置，也不是本文证明的一项独立模型质量收益。

如果服务平台的负载确实频繁在“读长上下文”和“长时间生成”之间变化，且 Agent 能暴露分叉、压缩和结束事件，值得试验这条路径。但基线应是调优后的静态配比，同时测首 token 和逐 token 延迟、P95/P99、吞吐、多租户公平性、故障恢复及缓存隔离，而不是只比较一个未经调优的默认配置。

## 对 GPU 超配选型的结论

本期两项分别减少初始化等待和改善运行中的阶段/缓存调度，没有完成“独立多模型权重与 KV 超配”的全面验证。对于这一特定目标，本轮仍未取得足够证据支持一项新的可交付方案；这不等于整个领域没有新进展。

选型时应先区分目标：需要快速补副本，关注检查点兼容性和恢复 SLO；需要减少 Agent 集群闲忙不均，关注真实负载的阶段比例与缓存生命周期。不要把同模型缓存复用、实例恢复和跨模型显存超配混为同一能力。
