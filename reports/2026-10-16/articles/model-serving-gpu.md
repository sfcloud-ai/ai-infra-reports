## KV 已复用，文本前端为什么还在重复计算

聊天每轮携带长历史时，GPU 可以复用前缀 KV，但 CPU 往往仍重新编码整段文本。Delta Tokenizer 针对这种追加式会话保留稳定前缀，只重做可能变化的尾部与新增文本。它不是任意段落缓存，也不能简单将旧 token ID 与新后缀 ID 拼起来：文本追加可能改变原来末尾的分词边界。[论文 v1](https://arxiv.org/html/2610.19801v1)

方法首先证明某个边界之前的编码稳定，再用替换补丁更新尾部。遇到完整长文，则在 tokenizer 允许的安全位置分块，让短任务能在块间插入执行；已开始的单块不会被抢占。历史被编辑、会话状态丢失或找不到安全切点时，需要退回完整编码。正确性要求逐 ID 一致，不能只检查解码后的文字看起来相同。[TokTier 0.3.0 发布说明](https://github.com/asu-idi/toktier/releases/tag/v0.3.0)

## 新版能接入，不代表默认全开

10 月 15 日发布的 TokTier 0.3.0 提供 SGLang adapter、CPU worker pool 和 append_patch。会话状态与工作进程是两层概念，不是每个会话新开一个进程；同样，启用会话增量也不等于自动开启所有分块优化。当期记录还指出，append_patch 虽向上返回局部补丁，native 交接仍有全量 Python list 成本，不能声称所有开销都只随新增内容增长。[0.3.0 实现限制](https://github.com/asu-idi/toktier/blob/v0.3.0/docs/releases/v0.3.0.md)

当期适配证据包括特定 SGLang 版本的小规模请求 ID 对照，不是所有 tokenizer、变体与 chat template 的普遍兼容承诺。固定 artifact、模板和库版本，覆盖 Unicode、特殊 token、并发续写、编辑历史、淘汰与重启，才是可重复验收的起点。

## 性能取决于瓶颈在哪里

作者报告 100K-token、warm-prefix chat 的中位 TTFT 约从 145 降到 60 ms，8K 时收益较小；若全新长文的 GPU prefill 主导，前端方案的 P99 差异不足 5%。极大的尾延迟倍数还包含超长请求分词后被拒绝的特定负载，不应当作正常长文服务收益。实验不是 4090/H20 的实测结果，短窗口、有限种子和 CPU 资源条件也限制了外推。[实验与限制](https://arxiv.org/html/2610.19801v1)

与 [GraphTok](https://arxiv.org/html/2610.13325v1) 相比，Delta 重点是减少重复 CPU 工作，GraphTok 则用 GPU 加速仍需完成的编码。前者要付 CPU 状态、内存和队列成本，后者要付传输、工作区及共享 GPU 争用成本。高并发既可能让 GPU batching 更有效，也可能使模型竞争或 CPU 池拥塞更严重，没有脱离负载的统一赢家。

本期建议先验证单实例串行增量，再考虑分块与进程池。强基线应保留快 CPU tokenizer 的真实热缓存；最终同时观察 ID 一致性、CPU 限额、状态内存、前端排队和 TTFT P99。若主要等待发生在 GPU，或会话大多无法复用历史，就应允许“不采用”成为正确结果。
