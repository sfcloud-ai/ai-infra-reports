# 模型服务与 GPU 超配｜KV 安全与达标成本

本文的 KV 缓存保存生成时复用的历史注意力状态；TTFT 是等到第一个输出 token 的时间，TPOT 是后续每个 token 的生成间隔。p99 表示 99% 请求不超过的延迟，SLO 是约定的服务质量目标。

本次截止时间为 2026-11-05 23:22 UTC（北京时间 11 月 6 日 07:22）。24 小时内未筛出证据完整且未报的本栏进展，扩至 72 小时后保留两项 11 月 4 日论文。它们分别补上“复用后的块是否仍属于这个请求”和“新增并发是否仍满足延迟要求”两条验收线，不是新的跨模型显存共享方案。

## KVGuard：地址没有越界，不代表 KV 没有串请求

![KVGuard：合法地址仍须检查请求权限，依据正文来源的原创简化示意图。](assets/kvguard-lifecycle.png)

多租户服务的危险不一定以 OOM 或 CUDA 越界结束。PagedAttention 通常先申请一整块 GPU 内存，再由引擎划分物理 KV 块。如果 CUDA Graph 的填充行沿用旧映射、卸载回来漏了一块，或者请求取消时过早释放仍在传输的 KV，访问地址仍可能落在合法的大缓冲里，却读到另一请求或上一轮生命周期留下的数据。普通 CUDA 地址检查不能表达“这一个请求此刻有没有权利读这一块”。[论文正文，§2–3](https://arxiv.org/html/2611.06138v1)

KVGuard 给每个物理 KV 块维护一份小型影子记录：一部分记请求的读写权限，一部分按条目记本次生命周期内是否真正写入。重新分配块时清空初始化记录，旧请求权限随释放撤销；前缀共享时只授予相应读权限。它沿五处边界检查：分配/共享/释放，CPU 块表构造，CPU 到 GPU 块表转换，kernel 内块表查找，最终 KV 读写。相比在整个 CUDA 缓冲外加红区，它检查的是服务实际使用的块、请求和生命周期。

对卸载与 P/D 分离，关键不是“拷贝调用返回了没有”，而是源和目的块在传输完成前不能被回收。发送端按读检查，接收端按写检查，并由发送端携带实际写入条目数；只把真正送达的条目标记为已初始化，短传输不能被当成整个预留块都已准备好。这个机制正适合用来审查显存超配引入的抢占、恢复和取消竞态，但没有增加显存容量，也没有代替调度隔离。[机制与实现，§4–5](https://arxiv.org/html/2611.06138v1)

**实验条件与真正的代价。** 实验为单张 H100 80GB、Xeon Platinum 8468 的 16 vCPU、Ubuntu 24.04、CUDA 13.0；vLLM 0.32.0 + FlashAttention 3，以及 SGLang 0.5.22 + FlashInfer 0.7.1。同一引擎关闭检查与开启全部五项检查、遇错中止模式对照。ShareGPT V3 覆盖 Llama 3.2 1B、Llama 3.1 8B、Qwen 2.5 14B 和混合状态 Qwen 3.5 4B，另以 1B 模型测试 LongBench 2K–8K 输入和五样本 MMLU。论文没有完整列出权重/缓存精度、输出长度分布及 H100 的 SXM/PCIe 形态，因此这些开销数字不能当作任意部署的容量计算参数。

Qwen 2.5 14B 的 TPOT 几何平均开销在两引擎上为 3.0% 和 7.4%；16 请求/秒下，p99 端到端延迟分别从 10.6→11.1 秒、12.7→13.8 秒。但“只增加几个百分点”不适合概括整篇论文：Llama 3.2 1B 在 24 请求/秒时，p99 TPOT 从 2.4→17.3 毫秒、4.0→17.4 毫秒；LongBench 2K–8K 输入在 16 请求/秒时，TPOT 放大 7.55 倍和 10.84 倍。短模型步骤与长上下文让逐步主机工作和检查成本显露出来。它更适合 CI、上线前验证和事故复盘，而不是默认全量在线开启。[评测，§6.1–6.3](https://arxiv.org/html/2611.06138v1)

内存也要拆口径。Qwen 14B 的 24 GiB KV 池对应 GPU 影子记录 9.1 MiB、主机 4.4 MiB；论文表中的约 0.05% 是两者合计相对于 KV 池的比例，不应全部写成新增 GPU 显存。Compute Sanitizer 对照除了全 kernel 检查，还有只检查 KV kernel 的调优版本，并关闭主机栈追踪；但为能运行，它将 GPU memory utilization 限到 0.50、KV 池缩至四分之一，只测 40 条提示的低请求率。因此不能拿该对照的巨大减速差，推导相同生产容量下的端到端收益。

**成熟度与下一步。** 论文回放了 29 个历史缺陷，并报告 8 个新的不安全状态转换。覆盖这组缺陷不等于证明所有 KV 访问安全：前缀哈希碰撞、量化缩放辅助元数据和分布式协调消息错误不在检查范围。论文称通过插件接入，但仍需在引擎和访问 kernel 的大量位置插桩；本轮未核实到可直接部署的官方 KVGuard 发布包或源码仓库，不能写成 vLLM/SGLang 已内置功能。

对当前独立多模型部署，最值得先做的是把这种检查思路转成恢复路径测试：分别限制每个模型自己的 KV 池，强制触发卸载、取消与恢复，检查异步传输结束前块是否仍被持有，再比较恢复结果与隔离执行。权重、KV、循环状态、通信缓冲和 workspace 仍按每个模型分别记账；H200 或其他 GPU 上的运行开销须重测。

## ServerBench：更多请求完成，并不等于更多合格服务

![ServerBench：只把达标请求计入服务收益，依据正文来源的原创简化示意图。](assets/serverbench-closed-loop.png)

增加并发会提高 GPU 利用率，也会扩大 KV 驻留、排队和 prefill 对 decode 的干扰。只在短输入、固定 batch 或五分钟内测到吞吐改善，很容易把超出延迟目标的工作也算成收益。ServerBench 把实现和负载选择放在同一个实验里：冻结模型、GPU、工作负载及延迟目标，让开发者同时选择服务实现和活跃会话数，再对冻结产物做独立验收。[论文，§1–3](https://arxiv.org/html/2611.06841v1)

它回放有依赖关系的编码会话，保留输入/输出长度、多轮前缀、分支子会话及工具间隔。后续请求必须等依赖响应完成，因而慢响应会拖慢整条会话。原始内容被重建，空闲时段也有压缩，这是一种保留结构的回放，不是原样生产流量。得分是达到 TTFT 和 TPOT 门槛的已完成请求 token 价值，除以窗口内分配的 GPU 成本。未达标请求不给分，未通过模型忠实度和完整执行检查的系统不给成绩。

这比单点吞吐更贴近服务决策，但“dollars per dollar”仍是实验评分，不是利润：缓存命中的输入按完整输入单价计值，GPU 以每张每小时 0.82 美元固定计价；没有自动包含 CPU、内存、存储、网络、开发和运维费用。不同模型的 token 单价不同，也不适合把得分直接跨模型排成本名次。

**实验与基线。** 三种部署均是单个模型的独立任务：Gemma-4-E4B-it 使用 1×L40，Qwen3.5-9B 与 Qwen3.8-27B-INT4 各用 2×L40；最后一种 checkpoint 明确为 INT4。论文参考引擎为 SGLang 0.5.19 与 vLLM 0.28.0，SGLang 采用各模型 cookbook 配置，分别校准并发，并以 5 个独立 seed 的结果冻结目标。每个开发任务 8 小时，正式回放 1,800 秒、使用未进入开发集的 seed。这里的 2×L40 是分配资源，不代表所有候选都采用相同 TP 或复制方式；正文没有统一规定候选并行布局，不能补写 TP2。[§4.1 与附录 6–9](https://arxiv.org/html/2611.06841v1)

主表中，Gemma 最佳系统得分 2.97，参考 vLLM 为 0.61，即约 4.87 倍，工作并发也由参考的 8 改为 32。该倍数同时包含服务设计和运行点变化，不是同并发 kernel 提速。33 个任务中 22 个通过验证，13 个超过最强参考；不能把最佳个例概括为自动优化普遍可靠。更适合迁移到当前工作的是两个受控观察：同一冻结实现、并发和会话下，300 秒窗口得到的平均分比 1,800 秒高 1.42–1.70 倍；一个开发时看似有效的并发/调度方案在最终负载中，合格价值占比由 76.0% 降到 16.8%，说明抽样会改变是否真正过载的判断。

**恢复路径比漂亮的曲线更有价值。** 一次 Gemma 优化加入抢占与缓存恢复后，开发过程主动缩小缓存池，强迫平时很少运行的路径出现，结果发现未初始化存储污染输出。修复后用 NaN 填充空槽，确认无效位置不能影响有效计算，再把恢复后的输出与隔离执行比较；同一缩池压力测试从修复前 0/3 通过变成修复后 3/3。另有系统短提示通过，却让 315K-token 的合法请求永远无法准入。准入的检查因此必须覆盖“系统已经空闲，最大合法请求最终能不能启动”，不能只检查高并发时 OOM 是否减少。[§4.4–4.6](https://arxiv.org/html/2611.06841v1)

**成熟度与复现成本。** [官方仓库](https://github.com/Infini-AI-Lab/Server-Bench) 已提供任务、回放与验收流程、结果记录，主项目为 Apache-2.0，内含依赖保留各自许可。README 提醒 8 小时开发后还要给最终回放和私有正确性阶段约 1 小时，因此不是一张 GPU 跑几个 microbenchmark 的成本。精度、模型版本、推理策略、硬件改变后须重新校准目标；论文正确性检查只抽取 20 个问答、允许至多 0.1 的绝对准确率差等有限门槛，也不能视为对所有输入的形式证明。

H100/H200 及独立多模型超配可以借用这套验收方法，不能继承 L40 的得分。建议每次只改变一个容量或调度机制，同时固定请求语料与 seed，先验证全长输入、取消、抢占和恢复，再用至少 30 分钟闭环负载联合扫描并发、p99 延迟、OOM/恢复失败与总成本；为每个模型保留独立权重和状态预算。这是验证方法的迁移，不是跨模型共享缓存的证据。
