# 推理引擎每日变动｜排空请求与大 KV 池正确性

今天选两个影响服务可靠性的变化，而不是把所有合并都当新闻。vLLM 与 SGLang 各有一个新进展；DeepInfer 已单独核查并保留空状态。

## vLLM：缩容和升级时，不要把仍在工作的一半服务杀掉

### 实际问题

一个生成请求可能先排队、预处理，再开始计算；在分离部署中，还可能由一台机器读入提示词，另一台机器逐字生成。前者通常称 **Prefill**，后者称 **Decode**。两端之间要传递 **KV cache**——模型为后续生成保留的中间状态。

如果容器收到 `SIGTERM` 退出信号后很快结束进程，用户看到的可能是生成中断，或者 Decode 还没取到 KV，Prefill 就把数据释放了。健康检查不再接流量，并不自动保证已经接收的请求完成。

### 变化是什么

[vLLM #62967](https://github.com/vllm-project/vllm/pull/62967) 于 **2026-10-31 05:41:55 UTC** 合并，提交为 `5a233286c6318c6fa579d3aac02860f64fa28742`。原 gRPC 退出流程硬编码 5 秒，没有正确利用 `shutdown-timeout`。新流程先拒绝新的 RPC（远程服务请求），等待已经接受的请求，包括预处理和排队中的工作，再给 EngineCore 剩余预算加 5 秒进行收尾，并保留仍可能被 Decode 读取的 NIXL KV。已接收 RPC 最多等待 max(N, 5 秒)，其中 N 是配置的退出等待时间；到期请求仍会取消。EngineCore 也只在剩余预算加 5 秒内保留待取 KV，不是无期限保证所有 Decode 完成。

数据路径不是“立刻断开然后再等”：入口先停止接新请求，已有工作继续沿原路径执行，跨节点状态的生命周期要覆盖消费者读取。它改变的是退出协调与存活边界，不是每个 token 的计算速度。

### 实验怎么解读

PR 的复现使用 **两张 B300、Qwen3-0.6B、nightly 8e2beaa、`shutdown-timeout=60`、eager 模式**：

| 场景 | 原行为 | 修改后 |
| --- | --- | --- |
| NIXL Prefill 完成 8 秒后才开始 Decode | 0/32 token（请求失败） | 32/32 token |
| 长流式输出 | 419/4000 token | 4000/4000 token |

这些用例各运行一次，证明具体退出时序可被修复；它们不是吞吐提升测试，也不能证明 H100/H200 上任意负载的尾延迟或可用性目标已达标。默认 `shutdown-timeout=0` 的行为不因此变成自动长时间等待。

### 对交付的意义

这是滚动升级、弹性缩容和节点维护值得检查的路径。Kubernetes 的终止宽限时间应能容纳入口排空和引擎收尾预算；否则应用内部愿意等待，外部仍可能强制终止。接入前用自身的长请求、排队请求及分离部署读取延迟做退出测试，核对拒新时刻、存量完成数、KV 释放时刻和最终退出时间。

代码已进入主线，但当前可见稳定版本仍是 **10 月 18 日发布的 v0.32.0**；不要把这个主线提交当成已经包含在该版本中的开关。测试应固定包含修改的构建，不为这一修复额外堆叠无关内部补丁。

## SGLang：KV 池足够大时，地址乘法也必须足够宽

### 实际问题

模型服务把 KV cache 划成很多槽位。访问某槽位，需要计算“槽位编号 × 每槽跨度”。即使显存还有空间，若中间计算使用 32 位整数，足够大的编号仍会溢出，最后访问错误地址。这不是显存容量不够，也不是模型质量下降。

### 变化与边界

[SGLang #47029](https://github.com/sgl-project/sglang/pull/47029) 于 **2026-11-01 04:13:21 UTC** 合并，提交为 `8d12b65e541ac6d4513a8fad03fed877557702ca`。修复在计算地址前将槽位索引转换成 64 位整数，让 `slot × stride` 不再先在 32 位范围内溢出。

这与缩小 KV 池绕过问题不同：缩池会放弃本来可用的容量；正确的地址宽度允许该路径按既定布局访问大池。原生 Triton 已使用 64 位地址计算的路径不受这个具体问题影响，不能把它说成所有 SGLang 部署的共同缺陷。

### 复现与收益

主要复现配置是 **MI355X、PyTorch 2.11 / ROCm 10、aiter 285579b62、Llama 3.1-8B、FP8 KV 与 NGRAM 推测生成**，KV 池含 **3,503,271 token 槽位**。旧路径在约 210 万槽位后出现故障；2,097,152 这一边界对应此次 8 个 KV head × 128 head dimension 的跨度，并不是所有模型通用的固定上限。

修复后，**600 个请求、输入 512 token、输出 4096 token、并发 48** 的运行完成约 **246 万输出 token，耗时 1792 秒**。MI325X 上也有复现与修复测试；没有 NVIDIA 硬件验证，因此不能把这些结果直接转成 H100/H200/Pro5500 的结论。

四组内核耗时基本持平，主要收益是正确性和可用容量，不应宣传为推理加速。它也不创造物理显存：独立模型权重和 KV 状态依然需要分别计账。

### 应如何使用

如果服务正在使用对应 AMD/aiter 路径，且大 KV 池会进入相关索引范围，应把大索引、长持续运行和高并发回归纳入升级验证。已有 Triton 正确路径的部署不必为此重做架构。当前可见稳定版本为 **10 月 19 日 v0.5.22**，此次是后续主线修复，采用时要固定实际包含该提交的构建。

## DeepInfer：已核查，本次无合格新进展

已独立检查官方提交、PR 和当前 README。本窗口内没有发现可入选的新增实质变化；最新可见提交为 **2026-10-25 的 `553741557a57df44a46fb3ab72b6aafeaf945337`**。不把旧的框架介绍重新计作今天的新闻。

固定版本 README 描述的是离线推理，支持 DeepSeek-V4.1-Flash，硬件列出 SM100 / Ascend 950；完整服务需要的 KV 系统、VE/P/D 分离和跨 DP 负载均衡不包含在公开范围中。因此不能直接把它作为 vLLM/SGLang 在线服务的等价替代。
