显存不够、通信等待长、训练恢复慢，往往都被概括为“资源没用好”。本期三项研究提醒的是另一件事：把工作挪到别处以后，依赖并没有消失。决策前要查清新路径占用了谁的 CPU、显存和故障预算。

## RapidMoE：CPU 参与的是计算，不只是存储

RapidMoE 面向显存受限的低并发 MoE 推理，将专家计算在 CPU 与 GPU 之间拆分。低比特常驻部分、残差计算和同步点必须放在同一条依赖链上理解；不能把跨设备的非线性输出任意相加，就认为与原计算等价。[论文 v1](https://arxiv.org/abs/2610.01265v1)

作者的 R1 实验使用两张 A800 80GB、512GB DDR4-3200 和 PCIe 4×16，序列长 1K。相对 KTransformers，batch 1 的 decode 为 21.8 对 8.0 token/s；batch 4 为 43.6 对 10.5，后者是聚合吞吐，不能当成单用户速度。MMLU-Pro 为 83.8 对 83.9，AIME24 均为 73.3。这些局部质量对照不等于所有业务质量无损。

工程上应先为常驻权重、KV、临时区与安全余量分别记账，再讨论弹性扩容。CPU quota、NUMA 与后台内存带宽也要固定，否则省下的显存可能换来每个 token 的尾延迟。按当期核查，尚未确认可下载的官方实现，因此适合机制验证，不宜直接排入生产替换计划。

## GPU 发起通信：短控制路径也有执行成本

direct 路径由 GPU 准备队列并通知网卡，proxy 路径由 CPU 代为提交。前者减少交接，却消耗 GPU 的队列管理、轮询与寄存器资源；后者把工作移出 SM，但引入 CPU 调度和 NUMA 风险。[机制研究](https://arxiv.org/abs/2610.01380v1)

同一研究的空载小消息实验中，tuned proxy 可以更快；带载时 direct 又可能有更好的尾部。甚至只编入通信代码而不执行，也会使特定 streaming kernel 吞吐损失约 37%。因此要同时测通信与原计算，不能用一张空载延迟图替代整套服务。公开实验 transport 缺乏完整错误恢复，也不能直接当生产通信层。

## Leto：恢复成立，先要证明硬件和状态仍可信

Leto 用独立状态管理者保留训练分配，让训练进程退出后状态仍可被接管。作者在 72 张 A100 的故障注入实验中报告 6–19 秒恢复；13 万卡规模属于仿真，且假设故障均可在原硬件上恢复。[论文 v1](https://arxiv.org/abs/2610.00687v1)

这条路线值得通用训练平台借鉴，但不应归入具身训练或直接照搬到 KV 缓存。优化器状态与可重算 KV 的成本模型不同。先区分进程退出、设备 reset、整机失联，再验证旧执行者隔离、部分提交和恢复中再次失败。若状态管理者与训练进程会一起被驱逐，保留状态的设计也就失去了前提。
