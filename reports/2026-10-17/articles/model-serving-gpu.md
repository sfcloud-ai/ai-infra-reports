## 先问保存了什么，而不是省了多少

显存不足可以通过减少保留信息、压缩表示、卸载或重算缓解，但这些方法承担的风险不同。本期的 DropKV 与 LCT 分别代表有损 KV 删减和无损训练张量压缩。它们不是同一种内存回收机制，更不能把共同的“省显存”目标当作共用验收标准。

## DropKV：删掉仍可能有用的历史，需要质量预算

[DropKV v1](https://arxiv.org/html/2610.22130v1)估算删去不同 KV 对注意力输出的扰动，将组合选择简化为逐 token 打分。注意力分数本身不够，关联 value 的大小与方向也会影响输出。方法因此是在有限预算下选择保留内容，不是回收已经没有引用的缓存；即使删减过程没有程序错误，回答质量仍可能下降。

[作者固定版本代码](https://github.com/AozhongZhang/DropKV/tree/afb97c2af09418ca58399dba50e6f956bb8ef153)有 Triton 实现，当期也已存在 kvpress 算法路径，但后者的 PyTorch 实现不能继承作者 Triton 数字。尤其 19.8 倍来自 A100-80GB、128K 上下文、batch=1、5% KV 预算的打分 kernel，相对的是自身 PyTorch reference；同 batch 完整 prefill 最高约改善 9.9%，不是模型服务加速 19.8 倍。以上均为作者结果，本期没有独立复测。

工程上应先以完整 KV 为质量基线，再比较不同保留预算的任务正确率、长程检索和输入处理成本。只在对照质量可接受时，容量收益才有意义。为更大 batch 腾出显存产生的吞吐，与相同 batch 的执行优化也必须分别报告。建议将算法置于理解注意力语义的推理层，而不是让通用内存池根据字节压力擅自丢弃模型状态。

## LCT：保留全部数值，支付反复编码成本

[LCT v1](https://arxiv.org/html/2610.22179v1)把训练中暂时不用的张量压缩后继续留在 GPU，使用适合 GPU 的编码、解码与部分融合操作，减少一遇容量问题就向 CPU 搬运的需求。对照应包括不压缩、重算与 offload，而不是只看压缩率。无损表示不意味着零开销，训练会反复访问和更新这些张量，编码成本必须进入单步时间。

当期已发结论保留作者的 Qwen3-4B、3090、batch=1、序列长度 1,000 的数据：峰值 PyTorch allocated 显存约降低 23.8%，单步约慢 6.7%。[公开代码快照](https://github.com/Maxzhu123/Losslessly_Compressed_Tensors/tree/396b9d6fb725956cb0735a83b5de368319d0b823)可见 NanoGPT 路径，但当期缺少 Qwen 完整复现脚本，因此不能把论文结果当成现成通用训练组件。

本期将 DropKV 保留为长文推理质量与容量的对照候选，将 LCT 保留为训练容量预研。前者必须回答“少留信息会不会损伤任务”，后者必须回答“省下搬运与容量是否值得编码代价”。二者都不直接证明在线多租户容量或服务延迟已经改善，也都不构成具身训练专项进展。
