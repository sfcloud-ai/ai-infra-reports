# 推理引擎每日变动｜释放显存之后，缓存何时还能用

## vLLM：交还 GPU 时，可保留同权重的外置 KV

两套模型服务轮流使用同一张 GPU 时，交还显存和丢弃主机缓存是两件不同的事。比如服务 A 暂时让卡给服务 B。A 睡眠时必须交还设备显存，但它已经放到 CPU 的上下文缓存未必需要一起扔掉。KV cache 是模型此前处理文本留下的中间状态；只要还是同一权重、同一有效缓存身份，恢复时读回它，通常比把长提示重新计算一遍更有意义。

11 月 8 日，vLLM [#57810](https://github.com/vllm-project/vllm/pull/57810) 合入 [5efb24d5420b](https://github.com/vllm-project/vllm/commit/5efb24d5420b1f28737e4e8d1b62b354ddc18069)，将“回收设备 KV”和“清空连接器缓存”分开。最终接口是 sleep(level=1, reset_connector=False)，release_kv_cache_memory 也接受同一选项。默认值仍为 True，原来的清空行为不变。这里不能照抄 PR 正文早期版本的 clear_connector_cache 参数：合入代码与使用文档已经改用 reset_connector。

流程上，保留外部缓存不能只跳过一次删除。外置缓存的待完成写入仍可能读取 GPU KV，若先回收设备页，就可能读到失效数据。合入实现让同步 EngineCore 在需要保留连接器缓存时继续推进尚未完成的工作，再同步设备、执行缓存重置；重置参数决定外部 tier 是否一并清空。醒来后的请求可通过原有连接器加载保留下来的块。新增测试使用 OPT-125m、CPU offload、同步调度，并覆盖进程内和多进程两种运行方式：保留时命中完整前缀，清空时不命中，同时核对输出 token 一致。

它的增量不在于发明 CPU 缓存，而在于让已有 offload 层跨 GPU 交还继续有效。对于模型轮换或 rollout 与训练分时用卡，可减少恢复后的重复 prefill。本次固定实现的端到端测试覆盖 OffloadingConnector，不能据此推断所有外部连接器都有相同恢复行为；选型时仍要核对实际连接器与版本。各模型仍须独立预算权重、GPU KV 和 CPU 缓存；该选项不意味着模型之间可以共享权重或任意复用 KV，也没有增加多租户隔离保证。

最重要的使用限制是权重身份：当前块哈希不覆盖权重版本。训练更新权重后，旧 KV 即使 token 相同也可能失效。应保持默认清空，或严格按权重版本设置 cache_salt，阻止新请求匹配旧块。不要为了恢复更快而省掉这一条。

PR 正文给过 GB200、DeepSeek-V4.1-Flash、TP4、16 个约 19.5k-token 提示的缓存计数和延迟，但它描述早期参数及补丁组合，而且两组顺序运行、后组更热。本期不把其中的延迟差作为最终合入版加速承诺。更可信的验收目标是：同权重恢复确实读回缓存，换权重绝不命中旧块，待完成写入在显存释放前结束。H100/H200 仍需在自己的连接器、模型及负载上验证；最近正式发布列表不能证明该提交已经包含在稳定镜像中。

## SGLang：逻辑释放与物理复用分开，避免多卡选页随时序漂移

一个请求已经向 CPU 报告结束，不代表 GPU 的所有流水工作都结束。重叠调度会在处理第 N 步结果之前启动 N+1；后者还可能按已准备好的页表读取旧请求的物理页，并写入其下一状态。如果分配器立刻把物理页交给另一请求清零或整理，就会发生读写冲突。

11 月 8 日合入的 SGLang [#48852](https://github.com/sgl-project/sglang/pull/48852)，提交 [de3636131d17](https://github.com/sgl-project/sglang/commit/de3636131d1727b1397be98a42d58d5db95a0936)，针对启用 unified memory 和 overlap scheduler 的延迟整理池，改为“逻辑上释放，物理上待复用”。请求 ID 和映射可以在既有读后写屏障约束下归还；物理页则登记到最近一个已记录完成事件、但结果尚未处理的 forward 序号下。forward 指模型的一轮前向计算。

正常路径等待对应结果按顺序处理、完成同步后，再把物理页放入可直接使用的空闲表。如果新分配提前需要这些页，只等待所需的最早几个待回收批次，而非每次释放都让主机等待。容量检查统一把待回收页算作可用预算，真正写入时再遵守事件依赖。紧急整理先集中读取布局，再建立等待，避免在等待之后零散读取设备状态。

旧实现已经使用 CUDA event 与复用栅栏保护页面，并不是毫无保护。新增价值在于，旧实现通过每张卡本地 event.query() 的结果决定哪些页已空闲，多个张量并行 rank 可能因完成快慢而选到不同页。新选择主要依据相同的逻辑步骤与计数，让选页决策不依赖各卡那一瞬间的完成时序。普通静态池和 eager chain 不受这次变更影响。

公开服务测试使用 NVIDIA H200，驱动 595.71.05、PyTorch 2.14.1+cu130、FlashInfer 0.7.2、sglang-kernel 0.4.10；模型为 gpt-oss-120b，TP1、FA3、统一内存与重叠调度。输入/输出为 4096/512 的随机负载，200 个请求、并发 64、总 token 容量 120000。新实现两次为 1464.2/1463.3 输出 token/s、TPOT 32.84/32.86 ms；对照 main 为 1468.4/1465.0、32.74/32.80 ms。这是基本持平，不是吞吐提速。30000-token 容量下的完整 GSM8K 测试同样未显示显著精度差异；该 TP1 结果也不能替代多卡一致性验证。

成熟度仍是主线工程变更。作者明确留下部分请求状态提交、流水并行、非 CUDA 屏障及 P/D 失败接收释放等边界说明，PR 页面展示的 CI 状态也有失败，不能写成全路径竞态已解决或全部 CI 通过。适合的落地路径是先验证当前业务实际使用的统一池、抢占、HiCache 和 P/D 组合，关注页选择一致性、无错误复用及尾延迟，而非凭一个性能标签直接升级。

## DeepInfer：本轮未发现合格的新增已落地进展

已分别读取官方主线提交、最近 PR、release 列表、README 和固定版本部署 Q&A。主线最新仍是 11 月 3 日 Q&A 更新，已在历史晨报覆盖；新的平台与评测 PR 仍有未合并提案，不能写成已支持。公开版本仍以离线推理为边界，README 列出的硬件为 NVIDIA SM100 与 Ascend 950；完整在线 KV 系统、P/D 部署和负载均衡并未因此自动具备，不推断 H100/H200 可直接运行。
