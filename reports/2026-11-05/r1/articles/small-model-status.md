# 前沿小模型｜CPU 决策服务的收益，取决于空闲时间而非参数标签

事件时间：2026-10-29 13:13:15.767 UTC（北京时间 21:13:15.767），7 天扩窗条目，不是今日发布。核验：2026-11-04 23:18—23:24 UTC。相对 11 月 4 日 23:20 UTC 截止约 154 小时，未超过 168 小时。原文为 League 工程团队的部署实验，不是 Google 新模型发布，也不是通用能力 SOTA 声明。

## 为什么值得看

低流量服务即使每次推理很快，闲置副本也会持续计费。这个实验值得借鉴的是按真实到达率选择常驻设备：把范围明确的结构化决策放到 CPU，可能腾出昂贵 GPU 的常驻预算；不能据此把所有小模型迁到 CPU，更不能把激活参数当成权重驻留大小。

Google 的 DiffusionGemma-26B-A4B 是 MoE（每次只激活部分专家的模型），标称约 26B 总参数、4B 激活参数，不能按“4B”预算权重内存。提示先建立 KV 缓存（历史 token 的中间状态），生成画布（待填答案的一组位置）再以双向注意力访问上下文；后续画布完成后才追加缓存。结构化决策只取预设选项的概率，并非一般自由文本生成。[模型卡](https://huggingface.co/google/diffusiongemma-26B-A4B-it)

## 从两个引擎步骤变成一个

在 vLLM 原路径中，prompt prefill（读入提示并建立缓存）和单步画布求值分开执行。PR #61480 的 single_pass_reads 把已知答案模板接到最后一块 prefill，仍分别保留 prompt 的因果关系与画布的双向关系。只有单步读取、不要求 prompt logprobs，且画布与末尾 prompt 同时满足 token 预算和上下文上限，才走融合路径；否则回退。它减少一次完整前向，不是删除 KV、跨模型共享权重，也不是显存超配。

截至核验时，该 PR **open，未合并、未发布**；head 为 86e9aacb658bb2fc6580af57fa844d9136559ebc。代码明确拒绝非 CPU、pipeline parallelism、KV connector 和 KV offloading。不能把它安装到 H100/H200 上期待同样收益。早期 c3-standard-44、Xeon Platinum 8481C、BF16 验证还显示峰值 RSS 约 63 GiB，融合前后基本不变。[PR 与条件](https://github.com/vllm-project/vllm/pull/61480)

## 性能、成本与质量必须一起读

原文比较 vLLM v0.32.0 与加优化的构建，BF16 权重约 48.1 GiB；主配置为 Vertex AI us-east4 单副本 c4-standard-24，BF16、4,096 上下文；24 段合成对话、四种提问格式，16/32-token 画布，单次去噪。

- 并发 1 时延迟下降 18.8%，各格式 p95 为 645—813 ms；并发 20 时中位延迟已达 3.7—4.6 秒，不能把低负载结果当并发 SLO。
- C4 并发 10 成本为每千次 $0.088；但若每月只处理十万次，常驻副本摊销后是每千次 $9.96（约 $996/月）。满载单位成本不能代表低流量账单。
- JevBench 231 项中，优化使 C4 的 2 项决策改变。整体准确率差异不显著不代表逐条输出不变。

这里的 GPU 旧对照使用更早的 nightly、1,024 上下文，双 L4 还是 FP8，不能作等条件 CPU/GPU 胜负。以上是 CPU 专用实验，未建立 H100/H200 对照；Pro5500（型号待核实）无适配结论。[实验原文](https://huggingface.co/blog/LeagueLabs/optimizing-diffgemma-decision-model-vllm-cpu-i)

## 对当前服务工作的判断

这更适合候选集固定、低流量、允许整模型常驻主机内存的分类或路由服务。首先应量出自身到达率、突发并发、端到端 p95 与 RSS，再在相同精度、上下文、请求集下比较 CPU/GPU 的“每月常驻成本＋超时损失”，不要复用宣传中的倍数。上线验收还应保留逐样本标签及置信度变化，尤其检查阈值附近样本；平均准确率无法代替决策一致性。

若当前系统依赖 KV 卸载或连接器，该 PR 的限制会直接冲突，应停留在隔离实验，不进入现有生产链。本文不建议直接升级，也不把未合并补丁列为稳定版能力。SGLang、DeepInfer 对此 CPU 融合路径未在本条核实，不声称支持。
