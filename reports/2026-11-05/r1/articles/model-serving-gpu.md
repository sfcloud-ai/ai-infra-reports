# 模型服务与 GPU 超配｜先把索引和预填充峰值算进显存账

**本栏主项：LeanSparse；补充机制：Bevy。两篇均为 72 小时扩窗收录，不是 11 月 5 日新发布。** 不同模型的权重、KV（历史 token 中间状态）、循环状态和索引必须独立预算，本文没有跨模型共享权重或共享 KV 的收益假设。

## LeanSparse 把稀疏检索的索引键也移出长期驻留

LeanSparse 值得关注的不是再把 KV 搬到 CPU，而是补上了两笔经常漏算的账：**解码阶段一直留在 GPU 上的索引键，以及一个请求从进入到完成 prefill 之间的临时峰值。** 即使一次稀疏注意力只访问少量历史位置，未来查询仍可能访问先前跳过的位置，因此完整历史不能直接丢弃；“稀疏读取”并不等于“常数显存”。[论文，§1–3](https://arxiv.org/html/2611.04671v1)

### 机制如何工作

论文使用 DeepSeek-V4-Flash 的 CSA/HCA 混合注意力作为具体对象。CSA 以压缩后的历史做稀疏选择，历史索引键与供注意力计算的压缩 KV 是两套对象。LeanSparse 将这两套完整历史保留在主机内存，并分别改变两个阶段的数据路径：

- **Prefill：按层加载，而不是全部层同时驻留。** 两个 GPU 历史缓冲区交替使用：当前 CSA 层计算时，传输流加载下一 CSA 层历史；原缓冲区只有在 GPU 消费和必要写回结束后才能覆盖。新生成的压缩 KV 另有 staging ring，未完成压缩窗口的状态跨 chunk 保留。
- **Decode：先粗筛，再拿原始索引键复排。** GPU 保存 32 字节的 PQ32 码（用紧凑的乘积量化代码近似表示索引向量），原始 FP8 索引键连同 scale 为 132 字节，完整版本在主机。先留下 2K 候选，再用原始分数选 512 个位置。原始索引键缓存和压缩 KV 缓存分开，避免“进入候选但没进入最终注意力”的位置被误当成同一种缓存需求。
- **这些不是无损等价替换。** 粗筛或 miss 过滤排除的位置，后续精排无法找回；GPU 上的紧凑码仍随历史长度增长。代码本训练、完整页编码、尾页保存、两次依赖传输和生命周期同步都成为维护对象。[论文，§2.1、§4–5](https://arxiv.org/html/2611.04671v1)

### 实验到底证明了什么

实验使用 **4 张 NVIDIA H100、DeepSeek-V4-Flash、SGLang tensor parallelism**。正文没有完整给出实测机器的 H100 SKU/单卡容量、驱动/CUDA、引擎 commit 和权重精度；§4.2 的 H100 SXM TP4 是传输重叠模型，不能拿来补齐实测 SKU。

在线式多轮回放选取 128 个 Open-SWE 长会话，每会话 20 次调用，按每分钟 120 个会话的泊松到达回放；保留调用顺序和工具等待，输出最多 8K token。启用前缀缓存、混合 prefill/decode，prefill chunk 为 4K token，最多 128 个活跃请求。比较基线是作者移植到 V4 的 ECHO，**不是原开源 ECHO 的直接原样运行**；HiSparse 只支持 P/D 分离，所以不参加这组混合服务对比。

- 同一批 2,432 次后续调用，首 token 等待时间（TTFT）中位数 **21.6→0.6 秒**，p95 **28.19→1.74 秒**。
- 但逐 token 生成间隔（TPOT）中位数 **66.4→81.7 毫秒**，会话完成时间中位数仅下降 **17.7%**，总输出吞吐提高 **10.2%**。释放显存后更早接纳 prefill、容纳更大 decode batch，启动变快，却加长了共享执行步。不能把 TTFT 的约 97% 降幅写成用户任务快了约 97%。
- 另一个 **decode-only** 压力实验关闭前缀复用，先完成全部 prefill，再在稳态测量。950K 上下文时，相对 HiSparse 的最大测试并发为 **2.95 倍**、吞吐为 **2.14 倍**。这是各自容量上限下的吞吐，不是等并发比较，也不包含长 prefill 的代价。[论文，§6.1–6.3](https://arxiv.org/html/2611.04671v1)

质量检查覆盖 GSM8K、NIAH、LongBench v2 和 MRCR，在其测试中与原 SGLang 分数差均不超过 0.5 个百分点；这些任务使用 256K 上下文上限，**不能由此保证 950K 长上下文质量**。截至本轮检索，论文及第一作者主页没有提供作者实现/复现实验链接，GitHub 精确项目名检索也没有命中对应仓库；因此可以评估机制和实验设计，尚不能给出可直接部署的版本。[论文，§6.4](https://arxiv.org/html/2611.04671v1)；[第一作者论文列表](https://panzaifeng.github.io/publications/)

### 对多模型超配的判断

这项工作减少的是一个模型实例中每个请求的状态驻留和 prefill 峰值，**没有减少不同模型各自的权重，也没有证明多租户隔离或多模型在线 SLO**。在 H100/H200 上评估时，应先逐模型记录：权重、运行状态/KV、索引、prefill 双缓冲与 staging、CUDA Graph/内核 workspace、上下文和安全余量；将所有实例的峰值相加，再检查主机容量及并发传输带宽。

值得做的下一步是固定同一模型版本、精度、chunk 和并发，比较现有 HiSparse/ECHO 路径与新路径，同时把 TTFT、TPOT p95/p99、会话完成时间、准入失败/OOM、CPU 内存和有效主机带宽放在一起验收。在能取得实现后，先在单模型确定收益，再加第二个完全独立权重和状态的模型，检查传输竞争与一个租户突发 prefill 对另一个租户尾延迟的影响。H200 的更大显存可能降低原来的压力，但收益是否还覆盖粗筛与传输开销，需要重新测量。

## 补充机制 Bevy 先运行专家就绪的请求

Bevy 针对的是本地 MoE 专家卸载：同一模型的一批请求中，只要某请求所需专家已经就绪，就让它先走到后续层，尽早揭示**真实**专家需求；其他请求的专家读取同时进行。调度优先落后的层，同层就绪任务临时成批，避免完全逐请求执行重复读取同一模型权重。它与 FlexGen/FlexLLMGen 的大批量块调度侧重点不同：后者通过吞吐导向的权重/KV/激活卸载与大有效 batch 摊薄 I/O；Bevy 改的是一个 decode 步内部的跨层就绪调度。这里没有 Bevy 对 FlexGen 的直接对照实验。[Bevy，§3–4](https://arxiv.org/html/2611.04794v1)；[FlexLLMGen 的原始设计与限制](https://github.com/FMInference/FlexLLMGen)

![Bevy 的专家就绪请求调度，原创简化图](assets/bevy-ready-experts.png)

更重要的工程细节是，专家缓存项必须在引用期间 pin 住，所有 pending fetch 去重；释放发生在 GPU 计算结束后。为防死锁，启用 runahead 前要求缓存至少能容纳所有并发请求这一层选中的专家，且**不依赖专家恰好重叠**。这提供了有用的准入思路，但属于同一模型内部状态管理，不是租户间的硬隔离。

实验是 M6 Mac mini（24GB 统一内存）和 Jetson AGX Thor（128GB 统一内存），专家从 SSD 读取；Qwen3.6-35B-A3B、Gemma4-26B-A4B 均为 Q4_0。相同引擎内比较 llama.cpp、SpecMD、FineMoE，统一 SSD 布局与 8 个读取线程，并限制预取并行度。30% 专家缓存、2–16 并发的 40 组配置中，相对最快预取基线的 decode 吞吐为 **1.01–1.38 倍**；论文更高的 1.55 倍来自另一组缓存容量扫描，不能混用。

**限制决定其位置：**测量只取 512 个 decode 步的后 256 步，剔除了观察到 SSD 读取减速的步，也没有完整给出输入长度、TTFT 或线上尾延迟。它不是 H100/H200 实测；离散 GPU 上改用 CPU 内存供专家、或增加 CPU 专家计算，只是迁移方向。正文未提供作者实现链接，不能写成 llama.cpp 已合并支持。当前值得借鉴的是“真实就绪信息优先于预测预取”的调度原则，不宜据此替换现有线上 CPU offload。[Bevy，§5.1–5.2、§6](https://arxiv.org/html/2611.04794v1)
