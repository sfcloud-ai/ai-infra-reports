# 推理引擎每日变动｜先兑现缓存命中，再把草稿显存算全

**筛选时点：2026-11-05 07:20（UTC+8）。** 本期选择两项已合并、尚未进入已核验发布版本的变化：vLLM 处理“排队顺序毁掉即将发生的缓存命中”，SGLang 修正“草稿池实际分配大于预算”。它们都值得进入部署验收清单，但都不是跨模型显存超配方案。各模型独立权重、KV/循环状态、计算临时区及隔离余量仍须分别记账。

这里的 KV 缓存，是生成文本时保留的历史 token 中间状态；prefill（预填充）是读入提示词并建立这些状态的阶段，decode（解码）则逐个生成后续 token。两项更新分别处理准入顺序和容量账目，不应混为同一个性能优化。

## vLLM：冷请求别抢先挤掉后面马上要用的前缀

### 先看服务里会发生什么

一个编程助手刚处理完长代码仓库上下文，这些前缀还在 GPU KV 缓存里。队列中先来一个全新上下文请求，随后才是继续追问这个仓库的请求。如果严格先到先服务，前一个请求分配 KV 时可能淘汰后一个请求原本能命中的前缀。缓存明明存过，后续请求却要重新做长 prefill。增加缓存容量可以缓和压力，但不能修复这种“使用之前先被挤掉”的次序问题。

[vLLM #54625](https://github.com/vllm-project/vllm/pull/54625) 于 **2026-11-04 17:53:03 UTC（11 月 5 日 01:53:03 UTC+8）合并**，对应提交 [2a777ce](https://github.com/vllm-project/vllm/commit/2a777ce26e8315fa503ac5e88b595235d1c2b928)。新增的 cache-aware admission 在队列前部有限窗口内优先兑现已经驻留的前缀，而不是改变正在运行的请求或增加一个外部缓存层。

### 机制：先只读探测，再在有限槽位里重排

实际流程是：

1. 仅在 FCFS 调度、已开启前缀缓存、当前步骤允许 prefill 时进入该路径。priority 调度不启用它。
2. KV 使用率低于阈值时直接跳过。**最终合并代码的默认阈值是 0.5，窗口默认 0，即默认关闭。** PR 正文前部仍残留 threshold=0 的旧说明，应以[合并版本配置](https://github.com/vllm-project/vllm/blob/2a777ce26e8315fa503ac5e88b595235d1c2b928/vllm/config/scheduler.py)为准。
3. 只查看前 N 个排队请求；只对状态为 WAITING、尚未计算 token 的槽位打分。评分是可复用前缀的 token 数，较长者优先，分数相同时保留原顺序。
4. blocked 或已经部分计算的请求保持原索引，窗口以外不动。这里不是“任何请求都不能越过 blocked 请求”：测试明确把 cold、blocked、started、warm 换成 warm、blocked、started、cold，固定的是中间请求的槽位。
5. 真正准入仍走原分配流程。新探测函数不占引用、不分配缓存块，也不发缓存存储事件，避免只是排队打分就制造假事件。每步代价是一轮窗口内前缀查询；次序确实变化时还需遍历等待队列重建前部。

这些行为可在[调度实现](https://github.com/vllm-project/vllm/blob/2a777ce26e8315fa503ac5e88b595235d1c2b928/vllm/v1/core/sched/scheduler.py)和[缓存探测函数](https://github.com/vllm-project/vllm/blob/2a777ce26e8315fa503ac5e88b595235d1c2b928/vllm/v1/core/kv_cache_manager.py)中核对。

### 和已有方案的区别

这是单引擎内的准入顺序优化，不是新的缓存驱逐算法、跨副本路由器或权重卸载器。它利用已经存在的前缀缓存；如果请求没有共同前缀，或者队列很浅，就没有多少可保护的复用。它也不按 TTFT 目标打分，与为短请求设置时限、调整 prefill/decode 执行节奏解决的问题不同。

因此不应为“缓存命中率已经很高”就默认打开：收益来自命中在准入时能否真正兑现，而代价是冷请求被推后、CPU 查询成本和批组成改变。代码未增加冷请求 aging 或最大等待时间保证；有限窗口不能替代公平性和尾延迟验收。

### 证据怎么读：不能把两个选项的收益算给一个

机制测试用 48-token 提示、16-token 块、总共五块的缓存，故意使两份三块提示无法同时容纳。不开窗口时，冷请求先分配会缩短热请求的缓存命中；开启后热请求先准入，计算 token 数少于完整提示。测试还覆盖阈值、窗口尾部、固定槽位、priority/关闭前缀缓存，以及 Mamba 缓存规格下无可复用前缀时不乱排。这能支持具体行为，不能单独给出生产收益。

线上测量来自 **Kimi-K3 FP4、8×MI355X、TP8/DCP8 的 agentic-coding trace**。最有辨识度的一组是 nightly 76c6f3f2、关闭 KV offload、不设置 prefill cadence、threshold=0，每臂 2029 秒，只比较 window=0 和 16：
- 并发 44：p90 每用户输出速度 15.15→15.53 token/s（+2.53%），总吞吐按 GPU 归一后 10,818→10,821 token/s/GPU，几乎不变。
- 并发 48：相同速度指标 11.50→12.07（+4.95%），吞吐 10,384→10,279 token/s/GPU（−1.01%）。
- 同一无 offload 配置在并发 44 把窗口放大到 64，吞吐反而下降 12.9%，p90 每用户输出速度下降 8.6%。

这里的“p90 interactivity”是速度分位数，**不是 p90 TTFT，更不是最慢请求的等待上限**。该组输入是长上下文轨迹，未给出这两臂完整的输入/输出长度分布；PR 另给出的约 84k 输入中位数、278–301 输出中位数属于其他组合实验，不能偷换成这一组的精确条件。PR 中约 44% 的改善同时打开了另一个 prefill cadence 选项，不能归因于本项。H100/H200 没有这组性能数据。

## SGLang：草稿池不能用没算进去的显存，冒充更高 KV 容量

### 问题：启动能分配，不等于预算可信

部署 DeepSeek-R1 一类 MLA（用压缩潜在向量保存注意力状态）模型时，EAGLE/MTP 草稿用于提出候选 token，目标模型再验证。启用解码上下文并行 DCP（将解码时的长上下文工作分到多个 GPU）后，目标 KV 与草稿 KV 的地址空间和头复制方式不一定相同。如果容量规划只按“一层草稿”的字节数收费，而真实草稿池按 DCP 放大的行数分配，启动日志会给出漂亮的 token 容量，代价却是偷偷花掉留给激活和 CUDA Graph 的显存。流量还没有进来，安全余量已经被吃掉。

[SGLang #39799](https://github.com/sgl-project/sglang/pull/39799) 于 **2026-11-04 00:23:07 UTC（11 月 4 日 08:23:07 UTC+8）合并**，提交 [dff6a0c](https://github.com/sgl-project/sglang/commit/dff6a0c3accf310f70eab81be1220a27b732c96b)。这是预算正确性修复，结果会让一部分配置显示的 KV 容量下降，不能包装为“同显存容量增加”。

### 机制：把行数扩张与每行大小分开计算

当前非 DSA 草稿池沿用分配器的扩展逻辑 ID：当 DCP 为 d 时，草稿在每个 rank 上按 N×d 行定容；目标池则有自己的分片映射。旧预算分支只收取近似一层目标 KV 的费用，与真实草稿分配不一致。

修复后的流程是：
1. 计算目标模型每个容量 token 的 KV 成本。
2. 对相应 EAGLE/STANDALONE 草稿分支，先以 dcp_size=1 计算草稿每层的行字节数，再乘草稿层数及 DCP 展开的行数；若还有既有 HiSparse 地址扩张，则仍保留其倍率。
3. 用“目标成本＋草稿成本”重新反推 max_total_num_tokens，随后按现有布局分配池。
4. DCP=1 时保持原行为；修复不改模型内核和请求执行路径。

为什么不能简单把目标每层成本乘 d？MLA 草稿的 latent（压缩潜在状态）行大小与目标相同，但 GQA/MHA（分组查询／多头注意力）的目标 KV heads 会随 DCP 复制，草稿 heads 不按同样方式复制。直接沿用目标值还会把 GQA 草稿多算，浪费容量。本次[最终代码](https://github.com/sgl-project/sglang/blob/dff6a0c3accf310f70eab81be1220a27b732c96b/python/sglang/srt/model_executor/pool_configurator.py)将两个因素分开；[分配器](https://github.com/sgl-project/sglang/blob/dff6a0c3accf310f70eab81be1220a27b732c96b/python/sglang/srt/mem_cache/kv_cache_configurator.py)则显示真实行数为何扩张。

这一分支仍以 EAGLE/MTP 复用目标 attention 配置、每层 KV 结构相容为前提；不同结构的 DFLASH/DSPARK 在代码中另有按 draft 配置定价的分支。不能把这里的简化成本公式硬套到任意新草稿架构。

![草稿 KV 预算的原创简化流程](assets/draft-kv-budget.png)

### 现有替代办法与这次修复的范围

运营者以前可以降低 mem-fraction-static 或手动限制 token 数来留下余量，但必须为不同 DCP 档重新猜安全边界。本次让共享容量规划器按实际分配收费，更适合避免不同机器配置出现隐性超预算。

更彻底的另一条路线是只分配草稿实际会使用的物理行。[#43599](https://github.com/sgl-project/sglang/pull/43599) 涉及这种布局收缩及相关 attention/传输适配，但本次检索时仍为 open。**#39799 没有消除这部分行数膨胀，也没有替它宣布支持新的端到端路径**；它先使今天已经分配的内存有正确账目。

### 实验条件和最重要的限制

公开启动测量为 **amd/DeepSeek-R1-0528-MXFP4-v2、61 个目标层＋1 个 MTP 层、MI355X、TP8、EAGLE 三步/top-k=1/四个草稿 token、FP8 E4M3 KV**，默认 mem-fraction-static=0.7718。主要表格使用 dummy weights，记录 TP0 启动日志；DCP8 的真实权重启动也给出相近容量与相同空闲显存。

- DCP1：容量 5,035,505 token，前后不变。
- DCP4：4,842,479→4,618,980 token（−4.6%）；池分配后空闲显存 53.74→61.61 GB。
- DCP8：4,819,001→4,330,117 token（−10.1%）；草稿池 20.68→18.58 GB，池分配后空闲显存 43.69→61.76 GB。

DCP8 约 18.1 GB 的预留恢复，不只是草稿池缩小了约 2.1 GB，还来自降低总容量后目标池一起缩小。以该 61＋1 层例子理解，预算从 62 个层当量改为 61＋8=69 个；4,819,001×62/69 与修正后的容量吻合。这是偿还之前错误占用的激活余量，不是凭空释放同等可用 KV。

**这组 MI355X 配置修复前后都不能完成端到端启动**：非 DSA NextN 草稿保留 dcp_size>1，在 draft-extend CUDA Graph 捕获时进入 ROCm DCP 分支，最终在 AiterAttnBackend.forward_extend 的 k.shape 处失败。池分配在此前已完成，所以表格能核验预算，不能证明已解决在线服务、吞吐或 OOM。H100/H200 需要用实际模型、后端及 DCP 组合重新验收；该修复的通用预算代码不等于上述 GPU 测量可以直接迁移。
