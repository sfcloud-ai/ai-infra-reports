低比特权重解决了模型放不放得下的问题，却没有消除逐 token 生成的串行等待。[BitMTP v1](https://arxiv.org/html/2610.28500v1)把多 token 预测训练与 GPU 执行联合设计，让同一模型承担草稿与核验，并用专用打包内核、共享 KV 和 CUDA Graph 复用降低运行成本。对已有小模型产品，这比只报告预测多少个 token 更值得研究。

### 应该比较哪个质量起点

H20 上 Bonsai-1.7B 的 D8 hybrid，相对同后端 SFT AR 平均解码速度为 2.4 倍，五任务平均分由 47.36 到 47.91。但原始模型均分为 50.30，不能只从额外微调后的较低起点宣布“质量无损”。该实验还是单请求生成，并不覆盖动态批处理、拥塞或在线尾延迟。

Hybrid 达到置信门槛时可直接提交候选，因此不是严格无损投机解码。即便 spec 模式，不同宽度的 BF16 核验路径也可能产生不同序列；不能将标题中的速度统一解释为逐 token 等价。公开代码将严格序列 oracle 与默认执行路径区分开来，这些语义应在产品验证中保留。[固定实现](https://github.com/PolyU-VCLab/BitMTP/tree/745719743bcf55ab5807840c444162428647262e)

### 省步骤也可能增加成本

H20 上该模型峰值显存增加 538 MiB，额外训练、候选状态和图复用都不是免费的。接受率低时，提出和核验被拒绝的 token 会浪费计算。质量门槛、输出长度和停止条件不同，也会改变速度比较；单请求加速不必然让一个 GPU 承接更多合格请求。

因此当期判断是条件性验证，而非给现有大模型服务打透明补丁。先保持硬件、分词器、输入输出分布和停止协议一致，比较原模型、SFT AR、spec 与 hybrid 的业务质量；达标后再测完整请求延迟、并发和长上下文。把训练设备小时、转换与版本维护算入成本，才能决定是否值得迁移。论文和源码提供了可检查的路径，但本次历史整理未运行模型，不能据此承诺生产质量或容量。
