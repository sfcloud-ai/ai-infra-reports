算力服务的优化要过两道关：先证明慢在哪里，再证明改动释放的资源能够实际回收。Herschel 连接诊断与验证，PackServe 用延迟余量集中请求；两者都比“利用率提高了”提供更多决策信息，也都保留了明显代价。

## 诊断有结果以后，仍需隔离验证

Herschel 按需附着运行进程，组合 Python 调用、对象字段、加速器 API 和设备事件，再重建跨进程依赖。修复建议还要经过受控测试、专家审核与灰度，不能把自动找到低效模式理解为可以无人值守改生产代码。[论文 v1](https://arxiv.org/html/2609.40247v1)

作者的八卡 H20 实验使用 vLLM 0.29.0、CUDA 13.0，报告活动采样对 TTFT 的开销低于 0.5%、TPOT 低于 7%。这是采集成本，不是优化后提速。半年约 1.7 万 trace 中 23% 发现低效模式，也不代表平均节省 23% 算力。实际采用时应保留关闭采样、仅采样、加入改动三组对照，防止观察工具本身改变了问题。

## 减少活跃实例，可能让用户等得更久

PackServe 在网关依次检查容量、额外 prefill 重算与预测 TPOT，然后优先将请求放入 decode batch 更大的实例。其增量是显式利用服务延迟预算，而非首次做缓存感知或负载均衡。[论文 v1](https://arxiv.org/html/2609.33224v1)

在 64 张 H20、16 个 TP4 SGLang 实例、MiniMax M2.5 230B 的一小时回放中，相对增强版 llm-d，30/50ms 目标下活跃 GPU-hours 减少 16.8%/24.6%。生产观察则来自两个相隔一周的匹配时间窗：平均实例数下降 34.7%，平均 TTFT 同时增加 66.4%，不是随机对照。论文的分钟聚合 TPOT 指标也不是逐请求尾延迟保证。

决策指标应是成功且达到目标的工作量除以付费 GPU 小时。只有空出实例确实被缩容、交回共享池或承担其他负载，收益才可能进入账单。若只是把工作集中、空卡仍在付费，不能把 active GPU-hours 直接写成财务节省。上线前宜先影子路由，再按交互与后台任务分档灰度；TTFT 尾部越界时，即使实例数更好也应停止扩量。

## 专家副本和通信后端：把执行成本接回容量账本

同一组 GPU 的执行速度，不只取决于算力规格。热点专家是否集中在少数 rank、通信工作是否占用了计算资源，都会改变实际交付。MegaFlux 与 Purlin 的共同启发，是把计算放置和数据路径拆开评估；共同限制则是现有证据集中在特定 scale-up 互联域。

### 热点专家的副本要与 KV 争夺显存

MegaFlux 保留逻辑专家选择与权重，让 token block 在额外容量预算内转到专家副本执行。权重传输与计算重叠，反向阶段也协调副本梯度归约。它不是免费消除倾斜，复制成本、额外 HBM 和小负载退化都必须纳入预算。[论文 v1](https://arxiv.org/html/2610.00671v1)

作者在单 NVLink 域八张 B200、25% 额外专家容量的合成层级实验中报告前向/反向几何均值 1.45×/1.28×。另一个 vLLM prefill 实验只有 1.13×–1.26×，不能将层级数字改称整模型服务收益；小型倾斜反向案例还退化到 0.91×。适合先测高倾斜、大 prefill，并设置低收益关闭条件，而不是默认打开所有专家复制。

### 通信分层降低耦合，不保证每个报文都更快

Purlin 把 collective 语义、协调与硬件 copy/reduce 数据路径分开，已有公开接口与实现。其价值是让“做什么、何时做、怎样搬”可以独立描述，但仍需对照成熟的 NCCL。[论文 v1](https://arxiv.org/html/2609.36954v1)、[官方代码](https://github.com/purlin-project/purlin)

实验使用独立八卡 NVLink 服务器，而非跨节点 RDMA。H200 的四项 1GiB collective 均落后于 NCCL；1.5 请求/秒的显著 TPOT 改善处于过载积压区间，不能当作稳定入流下的 SLA。默认归约也非确定性，需要全 rank 一致开启相应模式。

选型应保留现有后端回退，按 collective、消息大小、并发、背景竞争建立性能面，再看作业总时间和请求尾部。只有端到端收益能覆盖维护、兼容与故障恢复成本，替换底层执行栈才有意义。
