# vLLM：先释放热身 KV，再捕获 CUDA Graph

**2026-11-12 部分晨报，核验截至北京时间 09:52。** 本文包含两项今日主线合并，尚未核实其正式发布版本。

## 大图捕获之前，热身缓存要让出显存

[vLLM #66523](https://github.com/vllm-project/vllm/pull/66523) 于北京时间 08:55:52 合并，提交为 [3319c629](https://github.com/vllm-project/vllm/commit/3319c629a148c8f7ce088445911d9db4119af134)。它针对 extensible KV cache 的启动路径：热身已经提交的物理 KV 块会占据显存，较大的 CUDA Graph 随后捕获时可能没有足够空间。

最终实现先缩回布局所需的最小提交块数，再捕获图，之后按捕获后的可用显存扩展缓存。最小值通常是 1 块，block-outermost 布局需要 2 块，不能概括为所有配置都强制保留一块。虚拟地址预留保持不变；这是启动阶段的内存生命周期修复，不是稳态调度吞吐优化。

PR 给出的对照使用单张 H100 80GB、Gemma-4-31B、gpu_memory_utilization=0.95，并开启多模态编码器 CUDA Graph。作者报告 max_model_len 为 4096 和 8192 时，原主线启动出现 OOM，修复后均启动并完成六个图像请求。这个证据适用于给出的模型与启动配置；不能推出 H200、Pro5500 或多模型混部已通过相同验证。

对模型服务的直接价值是把“KV 先占满、图再分配”的启动冲突拆开。验证时应同时观察图捕获峰值、最终 KV 块数与服务是否可用。不同模型的权重和运行状态仍独立占用显存，这项修复没有实现跨模型权重共享或显存超配。

## 配额留下的空闲，不再被误认为设备没有内存

[vLLM #66704](https://github.com/vllm-project/vllm/pull/66704) 于北京时间 08:43:21 合并，提交为 [63980fbf](https://github.com/vllm-project/vllm/commit/63980fbf1ead0215e2bfaf89da7399895725003a)。在 extensible KV cache 模式下，显式 gpu_memory_utilization 对引擎总占用施加上限，KV 只能使用上限内剩余空间。

最终告警条件包含显式设置的 0.7 < gpu_memory_utilization < 1.0，且被该设置保留的可用空间至少为 1 GiB。它还改善配额导致的内存不足诊断。此处采用最终 diff 的 0.7，未沿用 PR 旧正文的 0.8。

这项改动增加可解释性，不会自动提高配额。单卡多服务部署时，预留显存可能是有意为其他模型、临时张量或峰值留余量；收到告警后仍需先核对整卡预算，不能直接把参数改为 1.0。
